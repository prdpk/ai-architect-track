1.1 · Study
Sync vs Async — what actually changes on the server?

Sync (plain def): the worker thread is blocked for the entire duration of every I/O call. Our /ask endpoint calls Anthropic — that's 2–10 seconds of pure waiting. During that entire wait, the thread is idle and cannot serve a single other request. 10 concurrent users = 10 blocked threads = 10× the compute doing nothing.

Async (async def + await): the worker hits an await (waiting for Anthropic), immediately suspends that coroutine, and the event loop picks up the next incoming request. When Anthropic replies, the coroutine resumes from where it left off. One worker handles many concurrent I/O-bound requests — no extra threads needed.

Why it matters for our app specifically: almost all of our latency is I/O wait (embedding model, Chroma query, Anthropic call). There is almost zero CPU work. That's the exact profile where async pays the most. A CPU-bound workload (compressing images, training a model) gets no benefit from async — it needs more cores, not non-blocking I/O.

Key rule: async wins when you're waiting on the network or disk. CPU-bound work needs threads or processes, not async.
1.2 · Study
Stateless vs Stateful — why does it control horizontal scaling?

Stateless: no per-user memory lives inside the process between requests. Every request is fully self-contained — any running instance can handle it correctly. Our FastAPI app is stateless: it reads policy docs at startup, then each /ask request carries everything needed.

Stateful: user-specific data lives inside the process (e.g. in-memory conversation history). Requests must be routed to the same instance every time (sticky sessions). Adding a second instance doesn't help — users are pinned to one. Kill that instance and they lose their session.

The correct fix — externalise state: move session or history data into Redis or a DB. Now every instance reads from the same shared store. Any instance can handle any user. Restart or kill any one without losing data. That's true horizontal scale.

Architect test: can you kill any instance at random and restart it without losing anything? If yes → stateless. If no → find what's living in memory and externalise it.
1.3 · Study
Horizontal vs Vertical scaling — where does vertical stop being an option?

Vertical (scale up): give the existing machine more CPU, RAM, or disk. Simplest option — no code changes, no architectural decisions. Works well early on. But: every machine has a physical ceiling (AWS's largest EC2 instance tops out); doubling machine size rarely doubles performance but often more than doubles cost; resizing requires stopping and restarting the instance (downtime window).

Horizontal (scale out): run multiple copies of the service behind a load balancer. No hardware ceiling — keep adding instances as demand grows. Cost scales linearly. But: the app must be stateless (any instance handles any request); you add operational complexity (load balancing, health checks, service discovery, distributed logging).

In practice: go vertical first — fast and simple. Switch to horizontal when the vertical cost curve breaks, the hardware ceiling approaches, or downtime is unacceptable.
1.4 · Study
CAP Theorem — what is the real architectural decision?

C — Consistency: every read returns the most recent write, from any node. A — Availability: every request gets a response, even if some nodes are down. P — Partition tolerance: the system keeps working when nodes can't communicate with each other due to a network split.

Why P is not optional: network partitions are a physical fact in any distributed system — switches fail, cables are cut, cloud AZs lose connectivity. You cannot prevent partitions. You can only decide what your system does when one happens: reject requests (CP) or serve potentially stale data (AP).

CP systems (e.g. HBase, Zookeeper): refuse requests during a partition until replicas are consistent. Data is always correct. The trade-off: the service may be temporarily unavailable. Right for: financial transactions, anything where stale data causes real harm.

AP systems (e.g. Cassandra, DynamoDB default): keep responding during a partition, but some nodes may serve old data. The trade-off: eventual consistency. Right for: user activity feeds, product catalogs, anything where brief staleness is acceptable.

Single-node Chroma: CAP does not apply — no distribution, no network between nodes, no partition possible. CAP is only a distributed-systems concept.
1.5 · Study
Latency vs Throughput — can you optimise one without hurting the other?

Latency: the time taken to complete one request from the user's perspective (e.g. 2 s for a single /ask). Throughput: how many requests the system completes per unit of time (e.g. 30 requests/minute).

The trade-off — batching example: instead of calling Anthropic once per question, collect 5 questions and send one batched API call. The per-call overhead (auth, TLS handshake, routing) is amortised across 5 questions → throughput improves. But each user now waits for the batch window to fill before their question is sent → individual latency increases. Optimising one hurt the other.

When each matters: interactive UI → latency is the metric users feel (slow = bad UX). Bulk pipeline processing → throughput is what matters (latency per item is irrelevant if the whole batch finishes in time). Know which SLO your system is measured on before optimising.

Architect move: state whether you're optimising for latency OR throughput before proposing a solution — they often pull in opposite directions.

2.1 · Study
SQL vs NoSQL — when do you choose each for a financial platform?

SQL (Postgres, MySQL): fixed schema with well-defined relationships, ACID transactions, foreign keys, joins. The default for financial data — trades, accounts, ledgers — because correctness is non-negotiable. A trade that debits one account must credit another: that's a transaction, and SQL enforces it atomically.

NoSQL (DynamoDB, MongoDB, Cassandra): schema changes frequently, entities have few relationships, and the priority is horizontal write scale or global distribution. Good for: audit event logs (append-only, high write volume), user sessions, product/fund catalogs where schema evolves quickly.

Common mistake: assuming NoSQL = no consistency. DynamoDB has transactions and strong-consistency reads — they're opt-in, not the default. Always read the consistency model of any DB you choose.
2.2 · Study
Indexing — what does it do and what is the hidden cost?

Without an index: the DB scans every single row to find matches (full table scan). On 500M rows this takes seconds. With an index: the DB maintains a separate B-tree structure mapping column values to row locations, so it jumps directly to matching rows — milliseconds instead of seconds.

Composite index example: for WHERE user_id = X ORDER BY created_at DESC, an index on (user_id, created_at DESC) handles both the filter and the ordering in one pass. No extra sort step. The DB reads exactly the rows it needs, in order.

The cost: every INSERT, UPDATE, or DELETE must also update every relevant index. A table with 10 indexes pays 10× the write overhead. Too many indexes → writes slow down significantly, especially under high-volume ingestion (e.g. trade tick data).

Rule: index columns you query frequently; regularly audit and DROP indexes that aren't used — they slow writes for zero read benefit.
2.3 · Study
Sharding — what is the hot-key problem and how does it hit financial platforms?

Sharding distributes a large table across multiple DB instances using a shard key. All data for one key value lives on one shard. Example: shard trades by user_id — all trades for user 42 go to shard A, all for user 99 go to shard B.

Hot-key problem: when one key value generates far more traffic than others, one shard becomes a bottleneck while the rest sit idle. Financial platform scenario: a single institutional client executes millions of trades per day. Every write goes to shard A → disk I/O maxed, query latency spikes, that shard becomes a SPOF for that client while others are unaffected.

Fixes: choose a more evenly distributed shard key (e.g. hash of user_id rather than raw value); give high-volume accounts a dedicated shard or cluster; separate read and write workloads so bulk reads don't compete with writes.

2.4 · Study
Replication lag — what is a stale read, and when does it cause a real problem?

Setup: the primary DB handles all writes. Read replicas receive changes asynchronously — there is always a small delay between a write landing on the primary and appearing on a replica. This is replication lag.

Stale read scenario: a user submits a trade at T+0 (written to primary). They immediately open their trade history (query routed to a replica at T+1). The replica hasn't applied that write yet — the trade is invisible. The user sees a page refresh that shows their trade missing. This is eventual consistency, and in finance it erodes trust fast.

Fixes: Read-your-writes consistency — immediately after a write for a user, route that user's next read to the primary (or wait for the replica to confirm it has the write). Use replicas only for reporting/analytics workloads where a few seconds of lag is acceptable.

Rule: never route a user's read to a replica immediately after their own write unless your product can tolerate them not seeing their own change.
2.5 · SPINE (built into the app)
Cache-aside — 3 steps, 2 non-negotiable rules?

3 steps: (1) Check cache. Hit → return immediately, zero backend cost. (2) Miss → call backend normally, get the real result. (3) Store result in cache with a TTL, then return. Next identical request hits step 1.

Rule 1 — cache failure must never break the API: wrap every Redis read and write in try/except. If Redis is down, fall through to the backend. A caching layer is an optimisation, not a dependency — the app must work without it.

Rule 2 — tests must never touch real Redis: we discovered this live — a test stored "Mocked answer." in Redis under the key for "Is theft covered?", and the real app served that mock to a real user. Mock the Redis client in all tests via conftest. Test isolation is not optional.

Cache key design: normalise the question (strip + lowercase) then SHA256-hash it. "Is Fire Covered?" and "is fire covered?" hit the same cache entry. Include a version token if your documents change — a doc update should bust the cache.
2.6 · Study
CDN — what can it cache, and what can it never cache?

How a CDN works: edge nodes (servers geographically close to users) cache responses keyed by URL. The first request for a URL goes to your origin server; the CDN caches the response. Every subsequent request is served from the nearest edge node — your server is never involved.

Can cache — /static/index.html, JS, CSS, images: identical content for every user, doesn't change between deploys. A CDN dramatically cuts latency (edge node is 10ms away; your EC2 in us-east-1 is 200ms away for a European user) and removes static-asset load from your origin entirely.

Cannot cache — POST /ask: the response depends on the question text, the retrieved policy chunks, and the LLM output. Two users asking different questions get different answers. The CDN keys on URL only — it has no visibility into the POST body. Even two identical questions might legitimately differ if the policy documents changed. Application-layer caching (Redis) handles this because it controls the cache key precisely.

CDN = edge cache by URL for static, public, identical-for-everyone content. Redis = app-layer cache by semantic key for dynamic, context-sensitive responses. They solve different problems and both can be used together.
