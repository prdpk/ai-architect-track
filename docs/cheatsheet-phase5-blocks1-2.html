System Design Cheat Sheet — Phase 5 Blocks 1 & 2

AI Architect Learning Track  |  Read once daily  |  If you can answer every Q without looking, you own it.

Block 1 — Foundations
Sync vs Async — what's different on the server?
Sync (def): worker thread blocks for the full I/O wait (our Anthropic call ~2–10s). Can't serve other requests during that time.
Async (async def + await): worker suspends at the await, event loop picks up the next request, resumes when I/O completes. Same worker, many concurrent requests.
Stateless vs Stateful — and why does it matter for scaling?
Stateless: no per-client memory in the process. Every request is self-contained — any instance can handle it. Our FastAPI app is stateless.
Stateful: session data kept in-process (e.g. conversation history). Breaks horizontal scaling — requests must stick to the same instance.
Fix: externalise state (Redis, DB) so any instance reads it.
Horizontal vs Vertical scaling — limits?
Vertical: bigger machine (more CPU/RAM). Limits: hardware ceiling, cost curve (2× size ≠ 2× perf, often >2× cost), requires downtime to resize.
Horizontal: more instances + load balancer. Limits: app must be stateless; adds network/coordination complexity.
CAP Theorem — what's the real choice?
C: every read sees the latest write.  A: every request gets a response.  P: system works despite network splits.
P is unavoidable in any distributed system (networks fail). Real choice: CP (reject requests until replicas sync) vs AP (respond with possibly stale data).
Single-node Chroma: CAP doesn't apply — no distribution, no partition.
Latency vs Throughput — can you improve one without hurting the other?
Latency: time for one request.  Throughput: requests completed per second.
Often trade against each other. Example: batching LLM calls improves throughput (more work per API call) but increases per-user latency (wait for batch to fill).
Block 2 — Data Layer
SQL vs NoSQL — when do you pick each?
SQL (Postgres): structured schema, relationships matter, ACID transactions required → financial data, trades, ledgers.
NoSQL: schema changes frequently, minimal joins, need horizontal write scale → event logs, product catalogs, sessions.
NoSQL ≠ no consistency — DynamoDB has transactions, just opt-in.
Indexing — what does it cost?
An index lets the DB jump to rows instead of full-table scanning.
Composite example: (user_id, created_at DESC) — lookup by user + pre-sorted, no extra sort step.
Cost: extra storage + every INSERT/UPDATE/DELETE must update the index. Over-indexing slows writes.
Sharding — what is the hot-key problem?
Sharding splits data across DB instances by a shard key. Hot-key: one key (e.g. a single institutional client) generates disproportionate traffic → one shard overloaded, others idle.
Fixes: better shard key, dedicated shard for high-volume accounts, splitting read/write workloads.
Replication lag — what goes wrong?
Primary handles writes; read replicas catch up asynchronously. Replication lag = replica is temporarily behind primary.
Stale read: user writes at T+0, reads replica at T+1, sees old data.
Fix for critical paths: read from primary immediately after a write (read-your-writes consistency). Replicas are fine for reporting/analytics.
Cache-aside pattern — 3 steps?
1. Check cache. Hit → return immediately (no backend, no LLM).
2. Miss → call backend, get result.
3. Store result in cache (with TTL), then return.
Key rule: cache failure must never break the API — wrap in try/except.
Tests: always mock the cache client — real Redis in tests pollutes prod cache keys.
CDN — what can it cache and what can't it?
Can cache: static assets served identically to all users — HTML, JS, CSS, images. CDN edge node serves them without hitting your origin server.
Cannot cache: dynamic API responses like /ask — response depends on the question, context, LLM output. Use Redis (app-layer) for that, not CDN.
