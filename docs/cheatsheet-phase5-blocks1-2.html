1.1  ·  Study
Sync vs Async — what actually changes on the server?
Sync (plain def): the worker thread is blocked for the entire duration of every I/O call. Our /ask calls Anthropic (~2–10 s wait). During that wait, the thread sits idle — it cannot serve another request. 10 concurrent users = 10 blocked threads.

Async (async def + await): the worker hits an await (e.g. waiting for Anthropic), suspends the coroutine, and the event loop immediately picks up another incoming request. When Anthropic replies, the coroutine resumes. One worker can handle many concurrent I/O-bound requests.

Key insight: async is most valuable when the bottleneck is waiting on I/O (network, DB), not CPU. Our app is almost pure I/O-wait — ideal candidate.
1.2  ·  Study
Stateless vs Stateful — why does it control horizontal scaling?
Stateless: the process keeps no per-user memory between requests. Every request is fully self-contained — any instance can handle it. Our FastAPI app is stateless: no session data in memory.

Stateful: user-specific data lives inside the process (e.g., in-memory conversation history). Requests must go to the same instance (sticky sessions). Adding a second instance doesn't help — users are pinned to one.

The fix: externalise state to Redis or a database. Now every instance reads from the same store → true horizontal scale.

Architect rule: if you can't kill any instance and restart it without losing anything, your service is stateful.
1.3  ·  Study
Horizontal vs Vertical scaling — where does vertical stop?
Vertical (scale up): give the single machine more CPU, RAM, or disk. Simple — no code change. But: hardware has an absolute ceiling; 2× machine size rarely gives 2× performance and often costs >2×; resizing requires downtime.

Horizontal (scale out): run N copies of the app behind a load balancer. No ceiling — keep adding instances. Requires the app to be stateless; adds operational complexity (service discovery, load balancing, distributed tracing).

In practice: vertical first (simple, fast), switch to horizontal when vertical becomes too expensive or hits the hardware limit.
1.4  ·  Study
CAP Theorem — what is the real architectural choice?
C — Consistency: every read returns the most recent write, regardless of which node handles it.
A — Availability: every request gets a response (even if some nodes are down).
P — Partition tolerance: the system continues operating when network splits disconnect nodes from each other.

Why P is not optional: network failures are a physical reality in any distributed system. You cannot prevent partitions — you can only decide what to sacrifice when one occurs.

Real choice → CP vs AP:
  • CP: during a partition, reject requests until replicas sync. Data is always correct, but the service may be temporarily unavailable.
  • AP: during a partition, keep responding, but some responses may be stale. Service stays up; consistency lags.
Single-node Chroma: CAP does not apply. No distribution = no partitions = no trade-off to make.
1.5  ·  Study
Latency vs Throughput — can you improve one without hurting the other?
Latency: time taken to complete one request, from the user's perspective (e.g. 2 s for one /ask).
Throughput: number of requests the system completes per second (or per minute).

They often trade against each other. Example — batching LLM calls: instead of calling Anthropic once per question, wait and batch 5 questions into one API call. The API call overhead is shared → throughput improves. But each individual user waits for the batch to fill → per-user latency increases.

Architect move: know which one your SLO cares about. Interactive UIs → optimise latency. Bulk pipelines → optimise throughput.

2.1  ·  Study
SQL vs NoSQL — when do you pick each for a financial platform?
SQL (Postgres): structured schema, relationships between entities, ACID transactions, foreign keys, joins. Right choice for trades, accounts, ledgers — correctness is non-negotiable.
NoSQL (DynamoDB, MongoDB): schema changes frequently, few relationships, need massive horizontal write throughput or global distribution. Right for event logs, user activity, product catalogs.

NoSQL ≠ no consistency. DynamoDB has transactions and strong-consistency reads — they're just opt-in, not the default.
2.2  ·  Study
Indexing — what does it actually do, and what does it cost?
Without an index, the DB scans every row (full table scan). An index is a separate B-tree data structure that maps column values → row locations, so the DB jumps directly to matching rows.

Composite index example: (user_id, created_at DESC) for the query WHERE user_id=X ORDER BY created_at DESC — the index handles both the filter and the sort in one pass, no extra sort step.

Cost: extra disk space + every INSERT, UPDATE, DELETE must also update the index. Too many indexes → writes slow down significantly.

Rule: index what you query frequently; audit and drop indexes that reads don't use.
2.3  ·  Study
Sharding — what is the hot-key problem and how does it appear in finance?
Sharding splits data across multiple DB instances by a shard key (e.g. user_id). All data for one key goes to one shard.

Hot-key problem: one key generates far more traffic than others. In a financial platform: a single institutional client executes millions of trades per day. All those writes route to one shard → that shard is overloaded while others are idle. Latency spikes and failures appear for that one client while others are fine.

Fixes: choose a more evenly distributed shard key; dedicate a shard (or cluster) to high-volume accounts; split read and write workloads onto separate infrastructure.
2.4  ·  Study
Replication lag — what is a stale read and when does it matter?
The primary DB handles all writes. Read replicas receive changes asynchronously — there is always a small delay (replication lag). During that window, a replica may serve old data.

Stale read scenario: user submits a trade at T+0 (written to primary). They immediately query their trade history (routed to replica at T+1). The replica hasn't caught up — the trade is invisible. This is eventual consistency.

Fixes:
  • Read-your-writes consistency: always read from primary immediately after a write for that user.
  • Replica for analytics only: reporting and dashboards can tolerate slight lag — route those queries to replicas and keep primary load low.
2.5  ·  SPINE (built)
Cache-aside pattern — 3 steps, 2 rules?
3 steps:
  • Check cache. Hit → return immediately. No backend call, no LLM, no cost.
  • Miss → call backend. Get the real result the normal way.
  • Store in cache (with TTL), then return. Next identical request hits step 1.
2 rules that matter in production:
  • Cache failure must never break the API. Wrap every Redis call in try/except — if Redis is down, fall through to the backend.
  • Tests must never touch real Redis. Mock the cache client in all tests or they pollute production cache keys (we hit this exact bug).
Cache key = normalised (lowercased, stripped) question hashed with SHA256 so casing variants hit the same entry.
2.6  ·  Study
CDN — what can it cache, and what can it never cache?
A CDN caches responses at edge nodes (servers close to the user) keyed by URL. The next request for the same URL is served from the edge — your origin server is never hit.

Can cache: /static/index.html, JavaScript, CSS, images — identical for every user, doesn't change between deploys.

Cannot cache: POST /ask — the response depends on the question text, the retrieved documents, and the LLM output. Different users, different questions, different answers. CDN has no way to key on request body content.

Use CDN for static assets (edge cache by URL). Use Redis for dynamic API responses (app-layer cache by semantic key). They solve different problems.
